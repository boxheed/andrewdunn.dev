# Building a Personal AI Software Factory, Part 1: The Theory

There is a strange paradox in AI coding right now: roughly 90% of developers use AI tools, yet a report across 22,000 engineers found that high AI adoption coincided with fewer weekly deployments and a 242% jump in incidents per pull request. Making code faster to write is somehow making software harder to ship. The industry's proposed fix is the "AI software factory", an automated delivery system usually pitched to 200-person platform teams alongside benchmarks like StrongDM's $1,000-a-day token spend per engineer.

This series tests whether that same architecture works at the opposite extreme: a single Windows laptop (RTX 3050, VS Code Devcontainers on WSL2) and a $20 monthly Google One subscription with Google Antigravity, using zero extra cloud spend. Before building the reference implementation in Part 2, we need to look at what a software factory actually is, why faster code breaks delivery, and what changes when you run one on consumer hardware.

## A Potted History: We Have Been Here Since 1968

If "software factory" sounds like brand-new AI hype, it is worth knowing we have been trying to build one since the year before the Moon landing. Roughly every fifteen years, the phrase gets dusted off and reinvented:

* 1968: Bob Bemer at GE and Hitachi's Software Works try running programming like an assembly line with statistical quality control.
* 2004: Microsoft revives the label around model-driven frameworks, promising to stamp out applications from reusable blueprints.
* 2017: The US Air Force's Kessel Run turns it into hardened containers, DevSecOps pipelines, and continuous compliance.
* 2026: Coding agents arrive, and the label is back on every conference stage.

Every earlier wave shared the same underlying assumption: they industrialised the work around coding while leaving the coding step human. Putting an agent inside the implementation step finally broke that sixty-year assumption. Factory.ai's white paper estimates that a tenfold speed increase in writing code yields only about a 10% gain in overall delivery. Once a machine generates diffs faster than a person can read them, proving the code works becomes the main bottleneck.

## Toolbox vs Factory (The Control Loop)

Most developers today operate a toolbox: an agent completing code in an editor, a script summarising pull requests, and a human manually copying context between disconnected sessions. Addy Osmani defines a software factory as many harnessed loops running concurrently, fed by a queue of work and drained through a review gate into production, with humans owning the system from above.

* Setpoint (Intent): Specifications, Work Orders, and acceptance criteria.
* Controller (Agents + Harness): Coding agents and their rules, where autonomy multiplied by concurrency sets the gain.
* Plant (Your System): The running codebase, services, and data stores.
* Sensor (Verification): Linters, tests, runtime checks, and human code review.

Turn up the gain on a control loop while leaving the sensor slow, and the system oscillates and overshoots. That is what showed up in Faros AI's 2026 data: epics completed jumped 66.2%, while incidents per pull request spiked 242.7% and weekly deployments fell. There is an obvious caveat (Faros AI sells engineering analytics and measured observational correlations rather than a controlled trial), yet their Q3 follow-up confirmed the mechanics. Even as incidents per change settled to +14.5%, pull requests merged with zero review climbed to +76.3% and time in QA jumped 300.6%. The human sensor saturated and was bypassed.

Osmani calls the governing limit back pressure: a loop can safely hold only as much autonomy as you can cheaply and reliably verify. Even fast automated tests miss the slowest loop. Dex Horthy described taking HumanLayer's product fully lights-off with no human code review; months later the site went down, the agent could not fix it, and the cause was buried in code nobody had read in three months. Unit tests do not fire when architecture rots over time, which is why humans stay at the setpoint (defining intent) and on the slow architectural loop.

## What Changes on a Single Laptop

Paul Iusztin, who built a solo factory called Squid, puts the buy line for managed enterprise platforms at the point where engineers you do not personally supervise start running agents. At solo scale, a factory is just a disciplined set of files in Git: `AGENTS.md`, Architecture Decision Records, fast linters (under 30 seconds), unit tests (under two minutes), and modular files under 500 lines so agents stay inside their context windows.

Running that on a personal laptop comes with four practical constraints:

* Portability stops at the harness. Repository contracts, Devcontainer definitions, and local verification scripts transfer cleanly if you swap Antigravity for OpenCode, Pi, or Claude Code. Orchestration glue (subagent delegation, tool permissions, browser hooks) is tightly coupled to the harness and always requires rewriting.
* Stock Devcontainers are not sandboxes. Policy in a system prompt is a suggestion; guardrails hold only at an infrastructure boundary. A default VS Code Devcontainer still inherits outbound internet access, Git credentials, and read-write repo mounts. Real containment means restricting network egress, scoping credentials, and keeping held-out acceptance scenarios outside the coding agent's write path (via read-only mounts or post-push GitHub Actions) so agents cannot rewrite tests to pass. On Windows, keeping the repo inside the WSL2 Linux filesystem also avoids the severe Docker bind-mount I/O penalty on /mnt/c/.
* An RTX 3050 will not run your coding loop. With 4GB to 6GB of VRAM, any local model large enough to track multi-file specifications spills into system RAM and crawls. Local GPU compute is useful only for optional narrow utilities like embeddings, leaving planning and execution to cloud quotas.
* Quotas bring discipline and ceremony. A five-hour rolling quota forces bounded Work Orders with explicit goals and definitions of done, because vague prompts trigger retry loops that burn your allowance. Even so, quotas cause mid-refactor stalls, and writing a formal Work Order and ADR for a 30-line fix takes longer than editing the file by hand. Sometimes the fastest move is to bypass the factory altogether.

## Four Constraints for Part 2

Iusztin abandoned the first version of Squid because he chased 24/7 remote autonomy and built a monolith he could neither debug nor steer mid-run. In Part 2, I will build a working reference implementation incrementally against four constraints:

1. Build the sensor first inside the Devcontainer before adding parallel agent loops.
2. Split writer from reviewer using a fresh-context review pass so the model stops grading its own homework.
3. Isolate held-out acceptance checks outside the coding agent's write path.
4. Keep commands granular so any run can be halted or overridden mid-flight.

Enterprise guides recommend tracking cost per merged change and 30-day rework rate. On a flat-rate $20 subscription with opaque rolling quotas and small solo commit volumes, both metrics are too noisy to be useful. Instead, I will baseline three simpler numbers before turning the factory on: time to signal (edit to verified result), quota exhaustion rate, and the share of agent-authored pull requests that merge without manual edits. Part 2 puts these constraints to work on a real codebase.
