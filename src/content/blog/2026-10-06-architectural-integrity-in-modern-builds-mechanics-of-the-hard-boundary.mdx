A declarative build script eliminates imperative configuration from the repository, but it relies on an underlying invariant: the execution environment must be deterministic. If the runtime environment fluctuates across developer workstations or continuous integration agents, the build ceases to produce reproducible outcomes.

Environmental variance manifests in mismatched compiler versions, divergent build tool runtimes, skipped pre-commit validations, and unvetted third-party dependencies. When these factors are left unmanaged, the build system cannot guarantee consistency.

Architectural integrity requires hard boundaries enforced at execution time. Rather than relying on documentation or developer compliance, the build pipeline must interrogate its environment, provision local validation tooling, and enforce security policies synchronously.

## Fail-Fast Environment Interrogation

Build systems frequently execute in heterogeneous environments. Developers run local builds across different operating systems and JDK distributions, while continuous integration workers run on containerized agents. If a project requires Java 21 with specific language features, compiling against an earlier runtime or an incompatible Gradle version produces inconsistent bytecode or configuration errors.

Deterministic builds require fail-fast assertions evaluated at the earliest possible stage of the build lifecycle. The build must validate its toolchain before executing compilation tasks.

This is the architectural function of `gradle-sweeney-plugin`. Modeled on declarative rule enforcement, the plugin inspects the runtime environment and asserts conformance against specified constraints:

- Java runtime vendor and version specifications.
- Build tool (Gradle) runtime compatibility.
- Environment variables and system properties required for execution.

If any constraint fails, the plugin halts execution immediately. Evaluating these assertions during configuration prevents invalid toolchains from compiling code or polluting local caches with corrupted artifacts.

## Zero-Dependency Hook Provisioning

Enforcing architectural discipline requires catching non-compliant code before it enters version control. Formatting errors, non-standard commit messages, and failing unit tests should never reach the remote repository.

Git hooks provide the standard mechanism for client-side validation. However, traditional hook management suffers from two structural problems:

1. Hooks reside in the `.git/hooks` directory, which is not tracked by source control.
2. Hook managers typically require external runtimes (such as Python, Ruby, or Node.js) to be installed globally on every developer machine.

Requiring developers to manually configure local runtimes introduces friction and leads to inconsistent adoption.

The solution is to manage hook provisioning directly through the build tool. The `gradle-lefthook-plugin` automates this process by downloading the architecture-specific binary for the host operating system directly into the project cache.

When the build executes, the plugin binds hook installation to the build lifecycle. Developers do not need to install global package managers or configure local system paths. Running the build guarantees that pre-commit and pre-push hooks are registered and synchronized with the repository definitions.

## Synchronous Supply Chain Verification

Hard boundaries must also protect the project dependency graph. Modern applications are composed largely of third-party libraries, creating a substantial supply chain attack surface.

Security scanning is frequently treated as an asynchronous post-merge audit. External scanners run scheduled jobs or inspect deployed containers, producing reports days or weeks after vulnerable code has entered the main branch. This decoupled approach treats security as an external review rather than an architectural constraint.

A disciplined build treats vulnerability detection as a synchronous quality gate within the verification phase. By integrating `gradle-osv-scanner-plugin`, the build evaluates direct and transitive dependencies against the Open Source Vulnerabilities (OSV) database during standard test and verification tasks.

The build asserts policy constraints directly:

- Dependencies are audited against known vulnerability advisories during the build.
- Severity thresholds (such as CVSS ratings) determine whether an advisory triggers a warning or halts execution.
- If a dependency introduces a vulnerability exceeding defined tolerances, the build fails before packaging or publishing occurs.

Embedding vulnerability checks into the local build ensures that security boundaries are evaluated before code is committed or merged.

## Enforcing Architectural Invariance

An empty, declarative build script establishes a clear contract for what a project produces. Hard boundaries defend that contract by eliminating runtime variance:

1. **Environment assertions** ensure the toolchain matches exact specifications.
2. **Lifecycle-bound hooks** enforce commit and style standards locally without manual setup.
3. **Synchronous vulnerability gates** prevent insecure dependencies from progressing through the pipeline.

With execution environments and dependency graphs constrained by hard boundaries, the remaining challenge is artifact publication. The final article in this series examines how to structure releases as an automated, deterministic state machine.
